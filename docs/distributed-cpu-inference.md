# yllm 分布式 CPU 推理设计(层流水线)

版本:v0.2 ｜ 状态:设计 ｜ 目标:DeepSeek-V4-Flash(285B MoE, ~146GB)在 2-4 台 CPU 机器上 decode

## 0. 结论摘要

- decode 的瓶颈是**每 token 串行读权重**。V4-Flash 是 MoE(256 专家, 每 token 只激活 6),
  每 token 实际读取 ≈ **12.3GB**(dense 8.6GB + 路由专家 3.2GB + head 0.5GB),
  远小于 146GB 模型体积 → 单机 ~1 tok/s,分布式收益显著。
- 方案:**层流水线并行** —— 43 层按层切 S 段,每台只读自己的 12.3/S GB;专家在层内,
  切层天然覆盖专家负载(每层每 token 固定激活 6 专家)。
- 预估(每机 13GB/s,现实 ×0.7):

| 机器数 | 理想 tok/s | 现实 |
|---|---|---|
| 1 | 1.0 | ~0.7 |
| 2 | 1.9 | ~1.3 |
| 3 | 2.8 | ~2.0 |
| 4 | 3.8 | ~2.7 |

- 通信开销可忽略:激活 fp16 **8KB/跳**(hidden 4096),logits 129280 → **top-k 3KB**;千兆 <0.1%。
- 注意力无算力墙:sliding_window 128(局部)+ index topk 512(长程),每 token ~1G MACs。
- **前置依赖(占 80% 工作量)**:转换器/内核目前只支持 llama,需先支持 deepseek_v4
  架构(§9)。分布式管线本身只占 20%。

## 1. 为什么是层流水线(而不是别的)

| 方案 | 结论 |
|---|---|
| 层流水线(按层切段,段间传激活) | ✅ 每台机器独立读自己的权重段,带宽线性扩展;MoE 专家在层内天然被切分 |
| 专家并行(专家跨机分片) | MoE 理论上更优,但需全局路由 + 跨机 gather 被选专家,复杂度高;层流水线已能拿到主要收益 |
| 张量并行(每个 matmul 跨机切行) | ❌ 每 token ~80 次 all-reduce,延迟 + 通信全赔进去 |
| 数据并行(每台跑完整模型) | 单流速度不变,只加多用户吞吐 |

llf 格式天然支持:mmap + 层主序 + 4096 页对齐,`dir[layer]` O(1) 拿整层区间,
每台机器只访问自己的段 → 页缓存只吸收本段,无需物理切文件。

## 2. 架构

```
rank0 (master, 含 tokenizer + 采样)
  ┌────────────────────────────────────────────────────────────┐
  │ embed(gather, 便宜) │ 层 0..B0 (含层内 MoE) │ x(8KB fp16)▶ rank1 │
  └────────────────────────────────────────────────────────────┘
rank1..S-2:  收 x → 层 B(i-1)..Bi(含层内 MoE)→ 发 x
rankS-1:
  ┌────────────────────────────────────────────────────────────┐
  │ 收 x → 层 B(S-2)..42 │ final_norm │ lm_head(129280×4096 ≈ 0.5GB 全表扫描)│
  │ top-k logits(≤3KB) ▶ rank0 采样                            │
  └────────────────────────────────────────────────────────────┘
KV cache: 各 rank 只持有自己层段的 KV(MQA: kv_dim=512 → 2KB/层/token),零跨机
流水线: TCP 发送缓冲天然解耦 —— 稳态下 rank0 算 token t+1 时 rank1 在算 token t
```

- 每个 rank 同一份二进制,`--rank R --ranks S --master IP`;全部 mmap 同一 llf 文件。
- embed 是行 gather(16KB/token)放 rank0 无压力;lm_head 全表扫描 0.5GB 计入末段。

## 3. 每 token 数据流

```
decode / prefill 统一:
  ① rank0: token_id → embed → 层段0(含路由 6 专家)→ send(x, fp16, 8KB)
  ② rank i: recv(x) → 层段i → send(x)
  ③ rank S-1: recv(x) → 层段末 + norm + head → top-k logits → send(rank0)
  ④ rank0: recv(top-k) → sample → 下一个 token_id → 回到 ①
```

- prefill 与 decode 同一循环(设计文档 §4.3 机制每 rank 各自生效)。
- 首 token 延迟 = S × 最慢段时长(填满流水线),稳态吞吐 = 最慢段时长⁻¹。
- MoE 路由在层内独立:每层每 token 算 router(4096×256 小 matmul)选 6 专家,
  只读被选专家的权重块(页对齐子块,madvise WILLNEED 按专家块下发)。

## 4. 分片与负载均衡

43 层块 + embed(0) + final_norm(44) + lm_head(45)。MoE 专家在层内,且每层每 token
激活数固定(6),因此**按层切分即按字节均衡**;唯一需要单独核算的是末段额外读 head 0.5GB:

| S | 分配建议(块边界切断) | 每 rank 每 token 读取 |
|---|---|---|
| 2 | rank0: 0..21 (embed+22层);rank1: 22..42 + norm + head | ~6.1GB / ~6.2GB |
| 3 | 14/15/14 层,末段借 1 层给 head 找平 | ~4.1GB |
| 4 | 11/11/11/10 层,末段少 1 层抵 head | ~3.1GB |

原则:只允许在块边界切断;末段 = (43/S 取整 −1) 层 + head;embed 是行 gather 极轻,rank0 可多分 1 层。

## 5. 通信协议与开销

- 帧格式: `[4B magic][4B len][1B type][payload]`,type ∈ {ACTIVATION, LOGITS, TOKEN, DONE}。
- 激活: 4096 float fp32=16KB → **fp16=8KB**。
- logits: vocab 129280 × 4B = 517KB → **只发 top-K**(采样只需 top-p/top-k 集合,
  K=512: id+fp16 logit ≈ 3KB)。全量 fp32 在千兆下 = 4.1ms/token,没必要。
- 开销(每 token):4 台 = 3 跳×8KB + 3KB ≈ 0.2ms,占 token 周期(0.26s 理想)**<0.1%**。
- 背压: TCP 自带;每 rank 每 token 固定 1 收 1 发。

## 6. DeepSeek-V4-Flash 性能模型

参数:hidden 4096,43 层,64 头×head_dim 512,MQA(kv=1),vocab 129280,
256 路由专家(6/256)+ 1 共享,专家 fp4,其余 fp8,LoRA 注意力,q_lora 1024/o_lora 1024,
index 注意力(64×128, topk 512),sliding_window 128,1M context。

**规模**:专家 ≈ 277B 参数(fp4 → ~138GB);dense ≈ 8B(fp8 → ~8GB);总 ~146GB。

**每 token 读取**(decode 稳态):
| 项 | 大小/ token |
|---|---|
| dense: 注意力(LoRA)+ index + 共享专家,43 层 | ~8.6GB |
| 路由专家: 6/256 × 277B × 0.5B | ~3.2GB |
| lm_head(129280×4096, fp8) | ~0.5GB |
| 合计 | **~12.3GB** |

**吞吐模型 A:每机满 DDR 带宽**(每机 13GB/s, 8 物理核全开;现实 ×0.7):
| S | 每 token/机 | 层数/机 | 理想 | 现实(×0.7) | 首 token 延迟 |
|---|---|---|---|---|---|
| 1 | 12.3GB | 43 | 1.06 | ~0.74 | ~0.95s |
| 2 | 6.2GB | 21 | 2.1 | ~1.5 | ~0.5s |
| 3 | 4.1GB | 14 | 3.2 | ~2.2 | ~0.35s |
| 4 | 3.1GB | 11 | 4.2 | ~2.9 | ~0.3s |
| 8 | 1.5GB | 5 | 8.5 | ~5.9 | ~0.15s |
| 16 | 0.74GB | 2-3 | 16.9 | ~11.8 | ~0.1s |
| 32 | 0.37GB | 1-2 | 33.8 | ~23.7 | ~0.06s |

**吞吐模型 B:按每机线程数 T 评估**

单机内存带宽-线程曲线(实测, yllm AVX2 decode 换算 GB/s):
| T(线程/机) | 1 | 2 | 4 | 8(物理核) | 16(SMT) |
|---|---|---|---|---|---|
| BW(T) GB/s | 3.0 | ~6.5 | 9.6 | 14.6(峰值) | 13.3(过订阅回落) |

tok/s(S,T) = S × BW(T) / 12.3。二维表(理想, 括号为 ×0.7 现实):

| S \ T | 1 | 4 | 8 | 16 |
|---|---|---|---|---|
| 1 | 0.24 (0.17) | 0.78 (0.55) | 1.2 (0.83) | 1.1 (0.75) |
| 2 | 0.49 (0.34) | 1.6 (1.1) | 2.4 (1.7) | 2.2 (1.5) |
| 4 | 0.98 (0.68) | 3.1 (2.2) | 4.7 (3.3) | 4.3 (3.0) |
| 8 | 1.95 (1.4) | 6.2 (4.4) | 9.5 (6.6) | 8.7 (6.1) |
| 16 | 3.9 (2.7) | 12.5 (8.7) | 19 (13) | 17.3 (12) |
| 32 | 7.8 (5.5) | 25 (17.5) | 38 (26.6) | 34.7 (24) |

要点:
1. **每机最佳线程 = 物理核心数**(8):SMT 16 线程因共享带宽反降 9%(13.3 vs 14.6 GB/s)。
2. **单线程机器无分布式意义**:S=32 也只有 7.8 tok/s,远不如 8 线程单机(1.2)→ 每台至少 4 线程起步。
3. **总线程 = S×T**:总带宽 ≈ S×BW(T),两轴乘法关系;但 S≥16 仍受 §6 的层粒度/固定开销/算力上限约束,
   32 台现实档 ~24 tok/s 是架构天花板,加线程也突破不了层粒度限制(每机 ≥1 层)。
4. 若机器内存带宽不同,按比例缩放:BW_machine = BW(T)/13 × 13GB/s 比例代入即可。

**S≥16 的收益递减与上限(重要)**:
1. **层粒度上限**:只有 43 层 + norm/head 可切,每机 ≥1 层是硬下限 → 最大有效 S≈43;
   S=32 已是 ~1.3 层/机,再往上只能靠专家并行或 head 张量并行。
2. **固定开销占比**:每机每 token 固定 ~2-3ms(收/发 + 小 matmul + 路由)。
   S=16 时占周期 5-10%,S=32 时占 15-20% —— 理想档位已不能直接乘。
3. **算力成为第二瓶颈**:总计算 ~15.6G MACs/token(专家 6.5G + dense 8.6G + head 0.5G),
   S=32 时每机 0.49G MACs,8 线程 fp8 约 40 GMAC/s → 计算 ~12ms,与内存 28ms 同量级。
4. **网络跳数**:S-1 跳 × 8KB + logits 3KB → S=32 时千兆 ~2.1ms(6-8%),万兆可忽略。

**结论**:满 DDR(每机 8 线程)下 4-8 台是性价比甜点(2.9→5.9 tok/s);16 台 ~12;
32 台 ~24 且接近架构上限,再往上需要专家并行/头部张量并行或 MTP 投机解码。
每机线程数按物理核心数配置(8),SMT 无益;总吞吐 ≈ S × 每机带宽。
千兆网在 S≥16 建议升级万兆。

**长上下文**:注意力被 sliding_window(128)+ index topk(512)限死,每 token ~1G MACs,
不构成墙;KV(fp16)2KB/层/token → 32K context ≈ 2.8GB、128K ≈ 11GB、1M ≈ 88GB(不现实,
需 KV 压缩方案如 compress_ratios/哈希层,后续单独设计)。

**内存需求/台(4 台时)**:mmap 段 ~3.1GB + KV(4K ctx)0.35GB + 激活 <0.5GB → 轻松。

## 6.1 嵌入式/手机集群评估(树莓派、手机)

**前提**:ARM 无 AVX2 —— yllm 需 NEON 或依赖 aarch64 gcc `-O2` 自动向量化(标量内核
已按 ILP 优化,内存带宽受限场景下够用);fp8/fp4 内核仍是前置依赖(§9)。

**单台设备持续带宽**(实测量级,含散热降频):
| 设备 | CPU | BW 持续 |
|---|---|---|
| Pi Zero 2W | 4×A53 1GHz | ~1.0 GB/s |
| Pi 4 | 4×A72 1.5GHz | ~3.0 GB/s |
| Pi 5 | 4×A76 2.4GHz | ~7.0 GB/s |
| 中端手机 | 8 核 LPDDR4X | ~10 GB/s |
| 旗舰手机 | 8 核 LPDDR5X | ~18 GB/s |

**台数估算**(tok/s ≈ 0.7 × S × BW_dev / 12.3 → S = 12.3×tok/s ÷ (0.7×BW_dev)):
| 设备 | 1.5 tok/s | 3 tok/s | 备注 |
|---|---|---|---|
| Pi Zero 2W | ~26(超层粒度上限) | 不现实 | 43 层硬上限,26+ 无意义 |
| Pi 4 | ~9 | ~18 | 4GB RAM 版单台存不下段,需 8GB 或 SSD |
| Pi 5 | ~4 | ~8 | 推荐:8GB 版,千兆网口,冷却散热片 |
| 中端手机 | ~3 | ~5 | 热降频后持续带宽掉 30-50% |
| 旗舰手机 | ~2 | ~3 | 存储 128GB+ 才能装段文件 |

**工程现实约束(比带宽更硬):**
1. **模型分发**:146GB 分 S 份(146/S GB/台)。Pi4@S=18 每台 ~8GB → 必须 SSD/大卡;
   手机 128GB 起步勉强够 S≤4。建议先做"层段预切分"工具,每台只存自己的段。
2. **网络**:Pi 5 千兆口;手机只有 WiFi(延迟 2-10ms,带宽几百 MB/s)。流水线稳态下
   每 token 一跳只传 8KB+top-k,吞吐微乎其微(0.3-0.7MB/s),延迟被流水线隐藏,
   WiFi 带宽不是问题,但 **20+ 设备同时连一个 AP 的稳定性**是问题。
3. **散热/供电**:手机持续满载 30 分钟必降频,带宽腰斩;树莓派需散热片+稳定供电。
   台数按降频后的持续带宽算(上表已含)。
4. **层粒度上限**:43 层 → 单流最大有效 S≈43;Pi Zero 2W 想上 3 tok/s 需要 50+ 台,
   已无意义,只能走专家并行。
5. **管理成本**:树莓派集群(PXE/K3s 式批量部署)远好于手机(无头配置、电池、App 保活)。

**NEON 内核已支持时(假设成立):**

关键认知:decode 是**内存带宽受限**而非算力受限,NEON 不改变 DRAM 带宽,
所以**所需台数几乎不变**。NEON 真正买来的是:

1. **带宽利用率系数 0.7 → ~0.85**:内核效率高,每设备更接近硬件带宽上限,
   台数按此重算(见下表,四舍五入后大多与标量版本相同)。
2. **每台所需线程数大降**:NEON 2-4 线程即可喂满设备带宽(标量要 6-8 线程),
   → 发热更低 → **手机/树莓派持续带宽不再因降频腰斩**,上表"持续带宽"得以兑现。
3. **fp8/fp4 解量化 + 路由 + 注意力开销变便宜**:S≥16 时的"算力第二瓶颈"消失,
   32 台现实档从 ~24 回升到 ~27;Pi 系设备在任何 S 下都纯带宽受限。
4. **Pi Zero 2W 依然不可行**(43 层层粒度硬上限不变)。

NEON 修正后的台数(系数 0.85, tok/s ≈ 0.85 × S × BW/12.3):
| 设备 | 1.5 tok/s | 3 tok/s | 相对标量 |
|---|---|---|---|
| Pi Zero 2W | ~22(仍超上限) | 不现实 | 26→22 |
| Pi 4 | ~8 | ~15 | 9→8 |
| Pi 5 | ~4 | ~7 | 4→8 减 1 |
| 中端手机 | ~3 | ~5 | 不变 |
| 旗舰手机 | ~2 | ~3 | 不变 |

工程结论不变:**Pi 5 × 8 ≈ 3 tok/s 仍是首选**;NEON 的意义不在省台数,
而在"每台 4 线程低功耗跑满带宽、手机不降频、32 台上限不塌"。

**结论**:实用方案是 **Pi 5 × 8(≈3 tok/s)或 Pi 5 × 4(≈1.5 tok/s)**,千兆网 + 散热片;
手机 2-3 台旗舰也能到 2-3 tok/s 但工程痛苦。V4 这种 146GB 模型在嵌入式上
本质是"带宽凑够"问题,台数 = 12.3×目标tok/s ÷ (0.85×单台GB/s)(NEON 已支持时)。

## 7. 流水线气泡与多请求

- 单流首 token 有 (S−1) 段气泡;稳态后无。
- 多请求:请求间错峰(请求 A 在 rank0 时请求 B 在 rank3),叠加吞吐。
- 多用户场景可用数据并行(每台全模型 + 不同用户),吞吐 ×S、延迟不变。

## 8. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 专家负载不均(路由偏向某些专家) | 偶发层读取偏差 | 专家子块页对齐 + LRU;统计热专家做常驻豁免(§3.7 设计) |
| 1GbE 下 logits 全量传输 | 每 token +4ms | top-k logits(§5) |
| fp4/fp8 内核缺失 | 无法运行 | §9 前置依赖 |
| 页缓存冷启动 | 首 token 慢 | 各段 `madvise(WILLNEED)`(ws_prefetch 机制按段生效) |
| 机器挂掉 | 整链停 | 简单主从检测 + 重启对端;MVP 不追求容错 |

## 9. 前置依赖(yllm 侧,占主要工作量)

1. **转换器支持 deepseek_v4**:当前 `convert_gguf.c` 只认 llama。
   需要:MoE 张量映射(256 专家按页对齐子块布局)、LoRA 压缩注意力、MQA(1 kv head)、
   head_dim 512、index 注意力、sliding window 配置、`ARCH_QWEN` 同级的 `ARCH_DEEPV4`。
2. **matvec 内核**:fp8 e4m3 解量化(dense 部分);专家实际存储量化待确认
   (GGUF 若用 q4_k 存专家,现有 q4k 内核可直接用)。
3. **MoE 路由执行**:router matmul(4096×256)+ top-6 选择 + 仅读选中专家子块
   + 专家 LRU/常驻豁免(设计文档 §3.7)。
4. **采样兼容**:top-k 集合采样(rank0);nextn_predict(MTP)首版忽略。

## 10. 实施路线

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | convert 支持 deepseek_v4 + engine 层段 | 分段 forward 与整段结果一致 |
| P0.5 | fp8/fp4 解量化内核 + MoE 路由执行 | 单机单进程跑通 V4 前向,与 HF 参考 logits 对齐 |
| P1 | 单机起 S 个进程跑通流水线 | 多进程输出 = 单进程输出;测出纯流水线开销 |
| P2 | TCP 传输层(千兆优先) | 2-4 台真机跑通,top-k 采样一致 |
| P3 | 调优:字节均衡分片、每机线程数、预取深度、专家 LRU、KV 压缩 | 达到 §6 现实档位的 80%+ |
